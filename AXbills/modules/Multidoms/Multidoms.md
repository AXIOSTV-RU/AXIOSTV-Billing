# Multidoms — анализ модуля и пригодность под несколько операторов

Дата разбора: 2026-08-14  
Статус модуля у нас: **не используется, в `@MODULES` нет, `MULTIDOMS_DOMAIN_ID` в config не задан.**

Это не DNS-домены. Это **тенанты биллинга**: у пользователей, админов, NAS, тарифов, групп, пулов IP и части настроек есть `domain_id`. Домен `0` — основная площадка. Остальные — изолированные кабинеты.

---

## 1. Что есть в дереве

| Путь | Назначение |
|---|---|
| `AXbills/modules/Multidoms/webinterface` | Админка и реселлерский UI |
| `AXbills/modules/Multidoms/reseller.cgi` | Отдельный кабинет реселлера/дилера |
| `AXbills/modules/Multidoms/config` | Пункты меню админа и реселлера |
| `AXbills/mysql/Multidoms.pm` | API доменов, админов домена, модулей, NAS-TP, отчёты по карточкам |
| `db/Multidoms.sql` | `domains_admins`, `domains_modules`, `multidoms_nas_tps`, триггер `domain_add` |
| `db/axbills.sql` → таблица `domains` | Список доменов (ядро, не только модуль) |

`form_purchase_module` в `webinterface` — не лицензия. Проверяет только, что `Multidoms.pm` есть и VERSION ≥ 1.05 (сейчас 9.21). При включении модуля компиляция пройдёт.

Зависимости UI: жёсткий `use Cards`. Реселлер завязан на Dillers и Hotspot.

---

## 2. Возможности модуля

### Админка (если включить Multidoms)

- CRUD доменов: создать / сменить / удалить.
- Набор модулей на домен (`domains_modules`) — у админа домена в меню остаётся только этот набор.
- Отчёт: сколько пользователей, тарифов Internet и NAS в домене 0 и в каждом тенанте.
- Привязка админа к доменам (`form_admins_domains` в `index.cgi`, если модуль в `@MODULES`).
- Суперадмин с правом `10` видит переключатель домена в шапке.

### Ядро без пункта меню

Поле `domain_id` живёт в ядре независимо от того, включён ли модуль.

- Если у админа `admins.domain_id != 0`, `cgi-bin/admin/index.cgi` всё равно грузит `Multidoms.pm` и режет списки по `DOMAIN_ID`.
- Кабинет пользователя: при `$conf{MULTIDOMS_DOMAIN_ID}` выставляет `ENV{DOMAIN_ID}`.
- Paysys: домен из `PATH_INFO` (`/123/...`), если модуль включён и задан `MULTIDOMS_DOMAIN_ID`.

### Реселлер (`reseller.cgi`)

- NAS и группы NAS в своём домене.
- Шаблоны/брендинг хотспота (`/images/{domain_id}/...`).
- Тарифы «на часы/сутки» (хотспот), не полноценный Internet-тариф.
- Привязка тарифов к NAS, перезапуск RADIUS (`$conf{RADIUS_RESTART}`).
- Публичная регистрация: новый домен + админ по телефону, пароль на почту.

### Триггер `domain_add`

При INSERT в `domains` создаёт три тарифа (`1 Hour`, `5 Hours`, `24 Hours`) и группу NAS `Default`. У тарифов **нет `MODULE='Internet'`** — старые time-limit планы под карточки/хотспот.

## 3. Работоспособен ли код

Как **каркас изоляции по `domain_id`** — да. Фильтры в Users / Nas / Tariffs / Payments живые.

Как **готовый продукт «из коробки» — нет.** UI заточен под хотспот-реселлера, не под оператора связи.

| Место | Состояние |
|---|---|
| Включение у нас | Нет в `@MODULES`, нет `MULTIDOMS_DOMAIN_ID` |
| Админский CRUD доменов | В целом живой |
| Карточка домена `info` | Шаблон `multidoms_domain_info.tpl` **отсутствует**, опечатка `DOOMAIN_ID` |
| `multidoms_nas_tps` | Кнопка «Изменить» пишет «изменено», **сохранения TP_IDS нет** |
| IP pools в реселлере | Функция есть, пункт меню закомментирован |
| Реселлерские тарифы | UI хотспота, в разметке ещё `DV_TARIF_PLANS` |
| Триггер | Создаёт тарифы без модуля Internet |

Для одного оператора с `domain_id=0` модуль **не нужен**. Включать «на всякий случай» не стоит: появится пункт «Домены» и риск, что админ с ненулевым `domain_id` увидит урезанный набор модулей.

## 4. Где в ядре есть `domain_id`

Изоляция сидит не в самом модуле, а в таблицах и фильтрах ядра.

Есть `domain_id` у:

- `users` — уникальность логина: `UNIQUE (domain_id, id)` (один логин может быть у двух доменов);
- `admins` — логин админа уникален **на всю базу**, не на домен;
- `groups`, `tarif_plans`, `nas`, `nas_groups`, `ippools`;
- `config` — настройки можно хранить на домен (`UNIQUE (domain_id, param)`);
- `payments` / `fees` — поля своего нет, фильтр идёт через `users.domain_id`;
- `bills` — **своего `domain_id` нет**, счёт это `users.bill_id`;
- `msgs_messages`, документы, часть Paysys (мерчант на домен).

RADIUS (`Auth2`): пользователь пускается только если `users.domain_id` совпадает с `nas.domain_id`. NAS без домена видит только домен `0`.

Супер-админ: `admins.domain_id = 0` → фильтр не ставится, видны все домены.

---

## 5. Задача: несколько операторов на одном биллинге

### Исходные требования

- Изолировать операторов: свои группы клиентов, лицевые счета, платежи, пулы IP.
- Супер-админы видят сразу всех.
- Выгрузки в СОРМ — всех.

### Уточнение (актуальное)

- Юрлица **разные, но дружественные**.
- Изоляция нужна, **без паранойи** (не отдельные базы и не железный контур).
- Банки будут слать **разные платёжные потоки** — здесь требования жёстче.
- СОРМ — **один канал**, но абонентов надо помечать как клиентов **разных операторов** (требование получателя выгрузки).

## 6. Оценка под уточнённую задачу

**Multidoms как раз подходит**, если не ждать от него банковский контур и СОРМ «из коробки».

### Изоляция кабинета — да

Дружественные юрлица, общий супер-админ, один биллинг — штатный сценарий `domain_id`.

Оператору не видно чужих клиентов, групп, тарифов, NAS и пулов. Супер-админ с `domain_id=0` видит всех.

Этого достаточно, если договориться: оператор не лезет в SQL/API мимо кабинета, супер-админы свои. Дыры в periodic и скриптах `misc/` при такой модели не критичны.

### Лицевые счета — достаточно для дружественных юрлиц

Таблица `bills` без `domain_id`. Счёт — `users.bill_id`. Деньги не смешиваются на одном счёте абонента. Отдельного «баланса фирмы» в биллинге нет — это бухгалтерия, не Multidoms.

### Банки — главный жёсткий контур

Paysys уже умеет настройки мерчанта на `DOMAIN_ID`: разные договоры, ключи, счета зачисления. Банк стучится в свой URL/магазин — платёж садится на пользователя нужного домена.

Зафиксировать с банками заранее:

- разные merchant ID / разные callback URL (у Paysys домен из `PATH_INFO`, если включён `MULTIDOMS_DOMAIN_ID`);
- поиск платежа не «по логину по всей базе» — логин уникален только внутри домена;
- сверка и возвраты — в разрезе оператора, не общим реестром.

### СОРМ — канал один, разделение операторов нет

Spectech **не знает** `domain_id`. Плагин крутится от системного админа и снимает всех абонентов.

Сейчас в каждую строку пишется один `$conf{SORM3_ISP_ID}` как `REGION_ID` (абонент, адрес, услуга, ident, платежи, IP-планы, шлюзы).

В формате Яхонт/Феникс `REGION_ID` как раз «оператор/филиал» из словаря «информация по операторам связи и их филиалах». Получателю нужно: абонент домена A → ISP 44, абонент домена B → ISP 45, файлы те же, FTP тот же.

Это **не новый СОРМ и не второй FTP**. Точечная доработка Spectech:

1. Таблица или конфиг `domain_id → SORM3_ISP_ID` (при необходимости регион/зона).
2. В `abonentGetNewData` (`AXbills/modules/Sorm3/Sorm.pm`) брать `users.domain_id` и подставлять свой `REGION_ID`.
3. То же в платежах, адресах, ident, IP-планах.
4. В словари «операторы и филиалы» занести оба юрлица.

Без этого выгрузка формально одна, но для получателя все клиенты одного оператора.

Iptv Periodic когда-то имел `DOMAIN_ID` — он **закомментирован**. На момент задачи проверить периодику остальных услуг.

## 7. Сводка

| Требование | Сейчас |
|---|---|
| Свои группы клиентов | Да |
| Свои тарифы / NAS | Да |
| Свои пулы IP | Да, если везде передавать `DOMAIN_ID` |
| Свои платежи в кабинете оператора | Да, как следствие клиентов |
| Свои лицевые как отдельный контур | Нет, только чужие uid не видны |
| Супер-админ видит всех | Да (`domain_id=0`) |
| СОРМ всех в одну выгрузку | Да, уже так |
| В СОРМ разные операторы (`REGION_ID`) | Нет, нужна привязка `domain_id → REGION_ID` |
| Банки / разные платёжные потоки | Paysys + домен, это главный контур, который надо сделать правильно |
| Гарантия, что оператор не увидит чужое вне UI | Нет (и при «без паранойи» не требуется) |

## 8. Когда задача станет реальной — порядок работ

Включать Multidoms «на будущее» сейчас **не обязательно**.

Когда понадобится:

1. Домены и админы операторов (`domain_id`, права, набор модулей).
2. Мерчанты Paysys по доменам, отдельные callback, поиск платежа только в своём домене.
3. Маппинг `domain_id → SORM3_ISP_ID` в SORM3 + словари операторов.
4. Проверка пулов IP, RADIUS (NAS.domain_id), периодики Iptv/прочих услуг.

Каркас `domain_id` в ядре для этой модели достаточный. Дыры самого модуля (хотспот-реселлер, недописанный UI, битый `nas_tps`, отсутствующий шаблон info) можно не чинить, пока не понадобится реселлерский кабинет.

Не делать: отдельные базы «на всякий случай», включать модуль без Paysys/СОРМ-маппинга, рассчитывать что триггер `domain_add` создаст нормальные Internet-тарифы.
